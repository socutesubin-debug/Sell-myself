# sell-myself: 자소서·포트폴리오 설명글 kit

사용자의 말과 메모 → 초안 → AI 티 제거 + 글자수 맞춤 → Markdown 문서. 이 순서를 지킨다.

## 실행 환경 두 가지

이 스킬은 두 곳에서 쓴다. 시작할 때 어느 쪽인지 보고 아래 경로를 고른다.

| | claude.ai 프로젝트 (기본) | Claude Code (레포) |
|---|---|---|
| 경험 은행 | 프로젝트 지식의 `experience-bank.md` (이름이 달라도 경험 은행 양식이면 그것) | 레포 루트 `me/experience-bank.md` |
| 스크립트 | 이 스킬 폴더의 `scripts/` (코드 실행 도구로 `python3` 실행) | `.claude/skills/sell-myself/scripts/` |
| 작업 파일 | 코드 실행 환경의 작업 폴더에 임시로 만든다 | `작성본/_메모/` |
| 결과 문서 | 다운로드할 수 있는 `.md` 파일로 만들어 준다 | `작성본/자소서/`, `작성본/포트폴리오/`에 저장 |

아래 본문의 경로는 Claude Code 기준이다. claude.ai에서는 위 표대로 바꿔 읽는다. 코드 실행 도구를 쓸 수 없는 환경이면 글자수를 한 글자씩 직접 세고, "스크립트로 세지 못함, 제출 전 사이트 카운터로 꼭 확인"이라고 결과에 적는다.

## 가장 중요한 규칙: 지어내지 않는다

자소서는 면접에서 검증된다. 그럴듯한 숫자 하나가 탈락 사유가 된다.

- 경험, 역할, 기간, 숫자, 회사·프로젝트·툴 이름은 **근거**에 있는 것만 쓴다. 근거는 두 가지뿐이다.
  1. 경험 은행 (claude.ai는 프로젝트 지식, Claude Code는 `me/experience-bank.md`. 없으면 `templates/experience-bank.md` 양식을 건넨다)
  2. 이번 대화에서 사용자가 직접 말하거나 붙여넣은 메모
- 근거에 없는 숫자가 필요해 보이면 쓰지 말고 **물어본다**. "전환율이 몇 % 올랐는지 기억나세요? 모르면 숫자 없이 쓸게요."
- "약 30%", "수십 명" 같은 어림값도 사용자가 그렇게 말했을 때만 쓴다. 정확한 값을 어림값으로 바꾸거나 그 반대로 바꾸지 않는다.
- 역할을 부풀리지 않는다. "참여했다"를 "주도했다"로, "도왔다"를 "이끌었다"로 올리지 않는다. 사용자가 쓴 동사를 존중한다.
- 감정·깨달음도 사용자가 말한 것만 쓴다. "이 경험으로 협업의 소중함을 깨달았다"처럼 아무도 안 한 말을 붙이지 않는다. 배운 점이 비어 있으면 물어본다.
- 대화 중 새로 들은 사실은 끝날 때 경험 은행에 추가할지 묻는다(자동으로 쓰지 않는다). claude.ai에서는 프로젝트 지식을 직접 고칠 수 없으니, 추가할 내용을 경험 은행 양식 블록(E번호 포함)으로 정리해 주고 사용자가 붙여넣게 한다.

## 시작할 때

1. 무엇을 쓰는지 확인한다: **자소서** 또는 **포트폴리오 설명글**(VIN 케이스 스터디 / Behance / PDF). 요청에서 분명하면 묻지 않는다.
2. 경험 은행이 있으면 읽는다. 없으면 양식을 건네고, 지금 받은 메모만으로도 진행할 수 있다고 알린다.
3. 아래 해당 절차로 간다.

## A. 자소서

### A-1. 문항 받기 (두 방식 모두 지원)

- **회사 문항을 붙여넣은 경우**: 문항 원문과 글자수 제한을 그대로 옮겨 적는다. 단위(공백 포함/제외)가 없으면 묻는다. 모르겠다고 하면 공백 포함으로 맞추고 두 수치를 모두 보고한다.
- **기본 문항으로 쓰는 경우**: `references/cover-letter-questions.md`의 기본 세트(Q1~Q8)에서 고르게 한다.
- 회사 문항은 기본 세트 중 가장 가까운 유형에 매칭해서 그 유형의 작성 요령을 적용한다. 예: "우리 회사에서 이루고 싶은 목표" → Q8 입사 후 포부. 두 유형이 섞인 문항은 둘 다 적용한다.
- 회사·직무 정보(인재상, 직무 설명, 채용 공고)는 사용자가 준 것만 쓴다. 회사에 대해 모르는 사실을 지어내 지원동기에 넣지 않는다. 필요하면 공고 내용을 붙여달라고 한다.

### A-2. 말투 고르기 (문항마다)

문항 목록이 정해지면 **한 번에** 문항별 말투를 묻는다. 기본값은 담백하게. 유형별 추천은 `references/tone-guide.md`에 있다. 예:

> Q1 지원동기: 담백하게(추천) / Q3 성장과정: 이야기하듯(추천) / Q5 성공 경험: 자신감 있게(추천). 바꾸실 거 있으면 말해주세요. 없으면 이대로 갈게요.

사용자가 말투 샘플(예전에 쓴 글)을 주면 humanizer의 Voice Calibration대로 그 목소리를 먼저 분석하고 선택한 말투 안에서 그 목소리를 따른다.

### A-3. 소재 고르기

문항마다 경험 은행에서 맞는 경험을 1~2개 골라 제안한다. 한 경험을 여러 문항에 겹쳐 쓰지 않게 배분표를 보여준다.

```
Q1 지원동기 ← E3 (○○ 리디자인)
Q5 성공 경험 ← E1 (△△ 앱 온보딩 개선)
Q6 실패 경험 ← (맞는 경험 없음: 질문 필요)
```

맞는 경험이 없으면 그 문항은 비워두고 질문한다. 억지로 다른 경험을 끼워 맞추지 않는다.

### A-4. 초안

- 문항 유형별 뼈대는 `references/cover-letter-questions.md`를 따른다.
- 첫 문장에 문항이 묻는 답을 둔다(두괄식). "저는 어릴 때부터~"로 시작하지 않는다.
- 초안 단계부터 목표 글자수의 90~100%를 노린다. 늘리기는 줄이기보다 어렵고, 늘리다 보면 지어내게 된다.
- 초안에서 쓴 사실마다 근거를 내부적으로 짝지어 둔다(E1, 메모 등). 이 짝은 최종 문서의 "근거" 표에 들어간다.

### A-5. AI 티 제거 + 글자수 맞춤

아래 "공통: humanizer 단계"를 따른다.

### A-6. 문서로 정리

`templates/output-cover-letter.md` 형식으로 `<회사명>_<직무>_<YYYY-MM-DD>.md` 문서를 만든다(저장 위치는 "실행 환경" 표). 기본 문항 세트로 쓴 경우 회사명 자리에 `기본문항`을 쓴다.

## B. 포트폴리오 설명글

`references/portfolio-formats.md`에서 매체별 구조·분량·말투 기본값을 읽는다.

1. **매체 확인**: VIN 케이스 스터디 / Behance / PDF. 여러 개면 같은 프로젝트를 매체별로 각각 만든다. 긴 것(VIN)을 먼저 쓰고 나머지는 거기서 줄인다. 줄이는 과정에서 새 사실을 더하지 않는다.
2. **프로젝트 사실 정리**: 기간, 팀 구성과 내 역할, 문제, 과정, 결과(숫자가 있으면 숫자). 경험 은행이나 메모에 없는 칸은 비워두고 물어본다. 특히 팀 프로젝트에서 **내가 한 부분**과 팀이 한 부분을 구분한다.
3. **말투**: 매체별 기본값을 제안하고 바꿀지 묻는다(자소서와 같은 3가지 중 선택).
4. **초안** → **humanizer 단계** → `templates/output-portfolio.md` 형식으로 `<프로젝트명>_<매체>.md` 문서를 만든다.
5. 이미지 자리는 `[이미지: 무엇을 보여줄지]`로 표시한다. 이미지 내용을 상상해서 설명하지 않는다.

## 공통: humanizer 단계

`references/humanizer/instruction.md`(korean-humanizer 원문)를 읽고 그 절차(트리아지 → 탐지 → 윤문 → 감사 → 등급)를 돈다. 패턴 전체 표는 `references/humanizer/ai-tell-taxonomy.md`. 이 kit에서 덧붙이는 규칙:

- **사실 장부가 humanizer보다 우선한다.** humanizer의 PERSONALITY AND SOUL 절("의견을 가져라", "곁가지·여담")을 따르다가 없는 일화·감정·디테일을 만들어 넣지 않는다. 목소리는 근거 안에서만 살린다.
- **장르는 자소서다.** 합니다체(또는 사용자가 고른 문체)를 끝까지 유지한다. "~했다" 체로 쓰기로 했으면 한 문서 안에서 섞지 않는다. 블로그체로 떨어지지 않는다.
- 자소서에 특히 자주 나오는 AI 티(자가검증 때 꼭 본다):
  - "~을 통해 ~을 배울 수 있었습니다", "~의 중요성을 깨달았습니다" 마무리 (A-2, I-4 계열)
  - "귀사의 ~에 기여하는 인재가 되겠습니다", "~에 이바지하고 싶습니다" 같은 막연한 포부 마무리 (D-6)
  - "소통·협업·책임감" 같은 3단 나열 (C-7)
  - 열정적인, 끊임없는, 주도적으로, 적극적으로 같은 형용사·부사 떡칠 (D-4)
  - "이러한 경험을 바탕으로" 같은 메타 연결 (A-6, H-3)
  - 문항을 다시 읊는 첫 문장("제가 ○○에 지원한 동기는~")
- **글자수**: 목표는 채용 사이트 제한이다. 넘으면 제출이 안 되므로 **목표의 95%~100%** 를 맞춘다(humanizer 기본 ±5%보다 엄격, 상한 초과 금지). 실제로 센다:

  ```bash
  python3 <스킬 폴더>/scripts/count.py <파일> --section "<문항 헤딩 일부>" --target 700 --unit with
  ```

  `--unit without`이면 공백 제외. 결과의 공백 포함·제외 수치를 모두 문서에 적는다.
- **늘려야 할 때**: 근거에 있는데 초안에 덜 쓴 사실을 풀어 쓴다(상황, 내가 고른 방법과 이유, 결과). 그래도 모자라면 질문한다. 꾸밈말이나 일반론으로 채우지 않는다.
- **줄여야 할 때**: 완충 표현, 문항 되풀이, 일반론, 중복부터 덜고, 구체적 사실과 숫자는 마지막까지 지킨다.
- **사실 검증**: 저장 전에 숫자를 기계적으로 대조한다.

  ```bash
  python3 <스킬 폴더>/scripts/fact_check.py <최종파일> <경험 은행 파일> [메모 파일]
  ```

  초안은 먼저 결과 문서 형식의 파일로 써두고 그 파일을 센다. 대화로만 받은 메모는 작업 폴더의 `메모_<날짜>.md`에 받아 적은 뒤 근거 파일로 넘긴다. claude.ai에서 프로젝트 지식 파일을 코드 실행 환경에서 열 수 없으면, 경험 은행 내용을 작업 폴더에 그대로 옮겨 적어 근거 파일로 쓴다. 숫자 말고 회사명·툴·역할 동사도 근거와 직접 대조한다. 걸린 게 있으면 고치거나 사용자에게 확인한다.
- 마지막으로 `—`, `–`, 이모지를 검색해 하나도 없게 한다.

## 사용자에게 보여주는 결과

대화창에는 짧게:
1. 문항별 최종본 (복사해서 바로 붙일 수 있게, 코드블록 말고 일반 텍스트 인용)
2. 문항별 글자수(공백 포함/제외)와 목표 통과 여부
3. 확인이 필요한 것: 질문, 근거가 약한 부분
4. 결과 문서 (claude.ai는 다운로드 파일, Claude Code는 저장 경로)

humanizer 탐지 목록과 등급은 문서에만 적고, 대화창에는 등급 한 줄만 쓴다. 사용자가 "결과만"이라고 하면 1번만.

## 고쳐달라고 할 때

"더 짧게", "이 부분 빼줘", "말투 바꿔줘" 같은 요청은 해당 문항만 다시 humanizer 단계와 글자수 확인을 거쳐 같은 파일을 갱신한다. 이전 버전은 문서 아래 "이전 버전" 접기 블록에 남긴다.
